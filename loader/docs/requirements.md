# Loader requirements

Requirements the loader owns. Requirements that span features, and the rule for where a requirement
lives, are in [`docs/requirements.md`](../../docs/requirements.md). Each ID is stable, unique across
every registry, and cited from code (`PROC-CITE-REQ`). A requirement that stops being true is
deleted, with every citation of it (`PROC-CURRENT-DEFINITION`).

## Content

Importing, storing and resolving measure content and value sets.

| ID | Requirement |
|---|---|
| `CONTENT-FHIR-VARIANT` | Knowledge tables store each FHIR resource in one `VARIANT` column, so nothing is lost and no schema is generated. A typed struct is not used: the Measure resource alone has thousands of fields. |
| `CONTENT-IMPORT-MEASURES` | One function, `cql_databricks.data_bindings.measure_import.import_measures` in the `cql-databricks` client, imports measures: FHIR `Measure`, `Library` and `ValueSet` resources (or Bundles of them) and value-set code rows the caller has read, as files into a `/Volumes` or `/Workspace` folder of the caller's own, never an environment's `knowledge` (`DEC-NO-CONTENT-PUBLISHING`). It writes `libraries/<Name>.cql`, `resources/library-<Name>-<version>.json` and `resources/measure-<Name>-<version>.json`, the resources as given, and `valuesets/<name>[-<version>].json`, one FHIR `ValueSet` per value set and version with its codes as its expansion, the layout the folder resolvers read (`CLIENT-KNOWLEDGE-RESOLVER`, `CLIENT-TERMINOLOGY-RESOLVER`). It fetches nothing. Before writing it checks every problem and reports them together (`check_import`): a Measure naming a Library not in the import or the folder, a value set a library declares with no codes in the import or the folder, a ValueSet that needs expanding, a library file in the folder holding another version of the library. Other resource types are counted as skipped. A dry run checks and writes nothing. A file it writes replaces the file of the same library or value set and version. |
| `CONTENT-IMPORT-SKILL` | One of the agent's skills (`SVC-MCP-SKILLS`), `agent/skills/import-quality-measures/SKILL.md`, guides a user through importing quality measures with `CONTENT-IMPORT-MEASURES` into a folder of their own: reaching and reading their content, getting value-set codes from a terminology service they name, choosing a folder they may write, a dry run, the import and a compile check that runs the measure from that folder. It never writes an environment's `knowledge`, and tells a user who asks to publish there that making content official is the implementer's process (`DEC-NO-CONTENT-PUBLISHING`). It names no content source; the agent reasons out where the content is from what the user says. It asks the user to confirm they may use the content under its terms. Served by `get_skill`, and published by `DEPLOY-AGENT-SKILLS` to the workspace skills folder and as a Unity Catalog skill. It installs the client wheel alone and holds no deployment value, since it is served verbatim: it finds the runtime Volume by its comment. |
| `CONTENT-IMPORTER-FHIR-SCHEMAS` | The shipped sources' FHIR resource schemas (`scripts/deploy/shipped_sources/src/shipped_sources/resource-schemas.json`) are the compiler's `dumpResourceSchemas` output, committed, so the synthetic population lands in the shape the compiler reads (`DATA-MODEL-SCHEMA`). `./gradlew checkResourceSchemas`, part of `checkAll`, fails when they differ; `./gradlew updateResourceSchemas` refreshes the copy. |
| `CONTENT-INCREMENTAL` | The deploy's writer of the `knowledge` tables (`scripts/deploy/shipped_sources/knowledge_tables.py`) MERGEs Measure and Library rows on (url, version), so loading the same content again loses nothing. A value set's codes replace that value set's earlier codes whole, keyed on `valueset_id`, so two loads sharing a value set keep one copy and a load never deletes a value set it did not bring. |
| `CONTENT-INGEST` | FHIR Measure, Library and ValueSet resources a caller has read are loaded with no dependency on an App or the engine, and nothing is fetched. A user imports them into a folder of their own (`CONTENT-IMPORT-MEASURES`); the deploy loads `examples/` into the default environment's `knowledge` tables after the same check (`CONTENT-EXAMPLE-PRELOAD`). |
| `CONTENT-LAKEHOUSE-STANDARD-ONLY` | Published tables are standardized FHIR resources or do not belong. Junctions and denormalizations are derived downstream. The published schema has no measure_library or valueset_ref. Valueset keeps tall shape (engine binding contract). |
| `CONTENT-MARKETPLACE-READY` | Table layout and provenance columns designed for eventual Databricks Marketplace publishing. |
| `CONTENT-MEASURE-LIBRARY-LINK` | The link from a Measure to its root CQL Library is derived from the Measure resource when read. It is an index with no truth of its own. |
| `CONTENT-NO-DERIVED-COLUMNS` | A knowledge table holds the resource, its identity and its provenance only. `url` and `version` are generated columns. Anything else derived from the resource is computed when read. |
| `CONTENT-SHARE-FAITHFUL` | Published knowledge stays faithful to FHIR spec including where inconvenient (base64 stays base64). Ergonomics live downstream of the share. Consumers derive optimized forms. |

## Synthetic data

The synthetic patient generator and the populations it produces.

| ID | Requirement |
|---|---|
| `DATA-SYNTH-LARGE` | The synthetic population large, the data of an environment of its own, `synthetic-population-large`, in its own catalog: about a million patients, 250,000 requested per pinned measure across the four pinned example measures (`loader/docs/synthetic-data.md`), generated by the patient data synthesizer at realistic rates, with one patient per manifest row carrying expected results. The cohorts are synthesized from the repository's own measures. Never the default environment. The recipe `loader/synthesizer/recipes/synthetic-large.json` defines the cohorts, their seeds and size, in the same shape as `DATA-SYNTH-SMALL`'s, and `scripts/generate-large-data.sh` generates, verifies and lands them, run only by hand. No build, test or deploy step runs it. `load.py` uploads each cohort's resources and manifest gzipped (`<Type>.ndjson.gz`, `manifest.jsonl.gz`) and reads only that form; a cohort found uncompressed in the volume fails the load. |
| `DATA-SYNTH-MARKETPLACE` | Not built. Planned after v0.3 (roadmap `DATA-SYNTH-MARKETPLACE`). A pre-generated synthetic population (`DATA-SYNTH-LARGE`), on the `DATA-CONTRACT` layout with synthetic markers (`SYNTH-PDS-SYNTHETIC-TAG`), is published as a free Databricks Marketplace listing. A deployment installs it as a catalog and tags it as an environment (`CLIENT-ENVIRONMENT`), so it is demoable from the first deploy without generating data in the workspace. One population serves every measure, so a shared library's results are computed once (`DEC-LIBRARY-OWNS-RESULTS`). The repository holds the generation Job, the install-and-tag step and the docs; the listing's provider profile is the publisher's. |
| `DATA-SYNTH-SMALL` | The synthetic population small, the data of the default environment, as tables in its `data` (`DEPLOY-DEFAULT-ENVIRONMENT`): roughly 1,000 patients per pinned example measure, defined in the synthesizer and run at a small scale to get people started easily. It is deployed with the project by default, not something they have to synthesize. It is the one example set. It is plausible, comprehensive data with no answer key; the answer keys are the conformance tests' (`compiler/conformance`). The recipe is `loader/synthesizer/recipes/synthetic-small.json`. The committed data is regenerated only by hand, with `scripts/generate-example-data.sh`, to update the project's sample data. No build, test or deploy step regenerates it. |
| `SYNTH-MODULE` | The compiler ships a synthetic data generation module: realistic synthetic healthcare data across multiple standards (FHIR first, generated from measure logic by `SYNTH-PDS-MODULE`), landed on the same `data-contract` so a generated source is indistinguishable from a customer source to the binding path. |
| `SYNTH-PDS-CORRELATED` | The solver instantiates related resources and solves temporal relations by pinning slots, supporting measures with multiple encounters, extension slots, and constraints on value sets or null values. |
| `SYNTH-PDS-DETERMINISM` | All randomness flows from one seed via `(seed, patient, site)` keying. Identical (measure, config, seed) reproduce byte-identical NDJSON and manifest; rows carry no wall-clock timestamp. |
| `SYNTH-PDS-FIXTURE-PINS` | Measure fixtures (ELM and valueset expansions) are generated on the developer's machine and pinned by SHA-256 in `cql_databricks_synth/pins.json`; the cache is rebuilt and verified against the pins at test time. |
| `SYNTH-PDS-IR-CONSUMER` | The synthesizer reads measure semantics from the Compiler's ELM only, walking the same ELM the engine compiles. It fails loud on unsupported constructs rather than approximating. |
| `SYNTH-PDS-MEASURE-CONFIG` | A measure's own realism lives in an optional `<Measure>.synth.json` beside its CQL, pinned with it (`SYNTH-PDS-FIXTURE-PINS`): population rates, weights over the branches of an `or` define, a plausible range per declared code or value set, and weights over value-set members. A route branch may be a define of an included library, named by the alias the measure includes it as (`Common.In Hospice Care`). Every key resolves against the measure's ELM or the load fails naming every unresolved key; a weight is positive, so every route and member stays reachable. It applies in the realistic mix only, a rate flag overrides it for one run, and its hash is part of the cohort identity. Adding a measure never edits synthesizer code. |
| `SYNTH-PDS-MODULE` | The patient data synthesizer generates coverage-directed synthetic cohorts from measure logic: enumerate population strata, solve constraints into skeleton patients, emit FHIR bundles with ground truth known by construction. Python command-line tool, offline, file-based. |
| `SYNTH-PDS-MULTI-LIBRARY` | The synthesizer handles multi-library measures with a full multi-library ELM interpreter, solving population logic via declared heuristic strategies and verifying 100% of patients through the full ELM. It is verified on the measures written for this repository. |
| `SYNTH-PDS-ORACLE` | Every generated patient carries an expected-results manifest row: the expected value of every define (true/false/null/value), computed by evaluating the bundle through ELM. Rows join against Runtime output for oracle-based validation. |
| `SYNTH-PDS-PRIORS` | Where measure logic leaves a choice open, realistic mode draws it from a distributional prior keyed to FHIR data or terminology, never to measure-specific rates, reweighting choices while keeping every route reachable. Measure-specific facts (route mix, quantity ranges, member weights) come only from the measure's config (`SYNTH-PDS-MEASURE-CONFIG`); the priors module holds no per-code range table. |
| `SYNTH-PDS-SCALE` | Cohort composition is derived from per-stratum count plans in three mix modes (uniform, realistic, explicit), and generation streams to files bounded by disk rather than memory, with 100% verification inline. The realistic mix takes each rate from its flag, else the measure's config (`SYNTH-PDS-MEASURE-CONFIG`), else the default. |
| `SYNTH-PDS-SKIPPED` | A route the solver cannot invert is skipped when a sibling route satisfies the same criterion; skips are recorded per stratum in `StratumOutcome.skipped_routes` and reported as patient counts in `coverage.md`. |
| `SYNTH-PDS-STRATA` | Strata are enumerated by scoring type (funnel first: IPP, denominator, excluded, numerator hit/miss, null membership). Contradictory combinations are reported `unsatisfiable` with conflicting constraint sites. |
| `SYNTH-PDS-SYNTHETIC-TAG` | Every emitted resource carries synthetic markers: `meta.security` set to FHIR security marker plus a generator-version `meta.tag`, so synthesizer data cannot be mistaken for real data downstream. |
| `SYNTH-PDS-TERMINOLOGY` | The synthesizer generates code from the same valueset expansions the runtime binds, so code membership is asserted at generation time and generator and engine never disagree. The expansions are the shipped measures' own value sets. |
| `SYNTH-PDS-VERIFY` | After fill, every patient (100%, never a sample) is re-evaluated through the same ELM and must land in its target stratum. Mismatch is a hard failure, never a quiet re-roll. |
| `SYNTH-SEED-OUT` | Data-source seeding is not part of the synthesizer; seed scripts live in `scripts/` as a separate loader feature. |
