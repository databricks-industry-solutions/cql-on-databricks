Verified data mapping

The compiler knows all of the FHIR it supports. Each customer publishes the part their data fills, through SQL that AI writes and a person approves. Paired checks prove the mapping: a CQL answer and a direct SQL answer must name the same patients.

Two changes on the roadmap

DATA-MODEL-SUBSET

Implementers own the shape

  • The compiler checks CQL against a superset: the FHIR R4 type graph for the supported resources, with no loop cuts.
  • A published view returns any subset of it, never an extra field.
  • The client reads each bound view's shape once per session. A compile gets it in its request, so it stays offline.
  • A real FHIR path the shape leaves out fails the compile, naming the path. It never reads as null.
DATA-MAPPING-VERIFY

Mappings are generated and proven

  • AI drafts SQL views or Lakeflow pipelines and explains them. A person approves, in a pull request.
  • Ground-truth checks pair a CQL expression with an independent SQL query over the source.
  • A check passes when both return the same patients, not only the same count.
  • Skills and tools for Genie Code and the agent, an App, and prebaked workflows.

Where they meet: the published shape is the coverage map. "Is this path mapped here?" and "will this CQL compile here?" are the same question, and every "not in this environment" error is the next mapping task.

What the design had to respect

Nobody hand-codes transforms

The user guides, AI drafts, a person reviews.

AI writes plain SQL and explains it in plain language. Reviewers read the explanation and the check results.

Transforms get messy

Patches pile up: a legacy feed, a clinic's odd codes.

SQL can be as messy as the data needs. The checks catch what a patch breaks.

CQL declares its model

using QICore '4.1.1' fixes the meaning of every path.

The compiler always runs against that model. Views fill a subset of it. No third model sits in between.

How a path is checked

One contract, a faithful FHIR resource (BIND-CONTRACT). A view returns the resource as a struct, resource, holding FHIR's fields only, and optionally the root columns patient_id (DATA-SUBJECT-KEY), min_date and max_date (BIND-PREFILTER). The engine's internals never reach an implementer: its lineage is not in the struct, since a resource's identity is its type and its own id (DATA-EXPORT), and its __* columns are refused, with no fallback (COMPAT-DATA). The engine passes resource through and never rebuilds it: measured 2026-11-03, a read that rebuilt the struct from root columns ran 18–23% slower, all of it Spark planning. The three root columns sit beside resource because Delta partitions on a top-level column and collects statistics on the first columns it meets. patient_id is a key, like a fully qualified key in an entity-relationship model: optional on every type, Patient included, and a promise that it is the id the other views' references name. A broken promise breaks joins with no error, as wrong dates drop rows.

Pruning already works this way at the top level. passes.RetrieveDemand lists the fields a library navigates, and the SQL back end treats that list as the contract a narrow mount is built to (EMIT-SQL-RETRIEVE-DEMAND-BOUND). The change takes demand down to full paths, so one analysis gives pruning, the shape check and data requirements. The shape's hash joins a result's identity, so a changed view never reuses an old score.

How a mapping is made and proven

A check pair, and a failure it catches

check · active-diabetes-2026Example on synthetic figures

CQL side

Runs through the published views and the compiler.

define "Active Diabetes":
  exists ([Condition: "Diabetes"] C
    where C.clinicalStatus ~ "active"
      and (C.onset as dateTime) before end of "Period")

SQL side

Written by the customer's analyst, over OMOP.

SELECT DISTINCT co.person_id
FROM   omop.condition_occurrence co
JOIN   omop.concept c ON c.concept_id = co.condition_source_concept_id
JOIN   check_codes.diabetes v
       ON v.vocabulary = c.vocabulary_id AND v.code = c.concept_code
WHERE  co.condition_start_date < DATE'2027-01-01'
  AND  coalesce(co.condition_end_date, DATE'9999-12-31') >= DATE'2026-01-01'

diagnosis
The 18 patients have a diabetes row that ended in January 2026. The view maps an end date to abatement with status resolved, so the CQL side drops them. The SQL side counts anyone active at any time in the year. The mapping is right and the check asks a different question. The analyst narrows the SQL to "active at the end of the period", and the check passes.

A failure can sit in the mapping, in the check or in the compiler. A compiler gap found this way gets a minimal conformance test with its fix, under the repo's existing rule.

Making the checks worth trusting

RuleWhy
Compare patient sets, not counts

Two errors can cancel in a count. A set difference names the patients to look at.

Record where the SQL came from

A person, an existing report, or an AI session that never saw the mapping. If one AI writes both sides from the same misunderstanding, they agree and are both wrong.

Same codes on both sides

A check states its value-set expansion. Otherwise a mismatch is about terminology, not mapping.

Synthetic patients and real data

Hand-made source records with known answers give exact tests on every change. Checks on real data run in the customer's workspace, as the caller.

Considered and set aside

OptionWhy not
Keep one fixed shape with cuts

Data beyond a cut can't be read, and widening the shape takes a release.

VARIANT for every resource

A view building VARIANT pruned nothing and ran 2.5 times slower. Typing a whole record at the mount crashed the warehouse. Wrong types surface while a measure runs.

An internal canonical model

CQL declares QI-Core, so a second translation is needed, and its meaning can drift.

A mapping language of our own

AI explains SQL more readably than a new language, and nobody wants to learn one.

FHIR StructureMap as the runtime

It runs resource by resource in a mapping engine, with no pushdown into source tables. ConceptMap stays, for codes.

Genie Code alone

It writes the SQL well, but without checks nothing proves it, and nothing stops a patch from breaking a measure. Here it is the drafting engine.
